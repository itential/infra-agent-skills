# Incident Management — Vendor Index

One row per supported vendor. Each vendor directory holds its own `procedure.md` (the full step-by-step),
plus wire-level `endpoints.md`.

| Vendor / Platform | Directory | Scope | Notes |
|---|---|---|---|
| ServiceNow | `servicenow/` | Create/read/update/assign/hold/resolve/reopen/close an incident (incident table, standard state model) | Also appears under `change-management`; the incident and change state models and close semantics differ, so the files are separate. Cancel, problem and major-incident handling, and the stored values for In Progress/On Hold/Canceled are not covered or not stated in the sources |
| PagerDuty | `pagerduty/` | Create/find/read, note, acknowledge, reassign, escalate, snooze, merge, resolve, reopen an incident (REST API v2) | REST; every write needs an acting user's email. Three statuses only (triggered, acknowledged, resolved): no hold and no separate close. Reopening through the API is unverified. Standalone on-call paging, services, escalation policies, schedules, event ingestion, status updates and responder requests are not covered. Creating an incident notifies responders through the service's escalation policy |
| Opsgenie | `opsgenie/` | Create/find/read, note, add responder, set priority/message/description/tags/details, resolve, close, reopen, delete an incident (REST API v1) | REST; every write is asynchronous and needs a request-status check. No acknowledge, assign or hold; ownership is by responders. Standard and Enterprise plans only; EU accounts use the EU host. Atlassian has announced end of sale and end of support for the product; those dates came from a search summary and are unconfirmed. Alerts, on-call and services are not covered |
| Jira Service Management | `jira-service-management/` | Create/find/read, comment (public or internal), assign, transition (resolve, reopen) an incident request (Cloud service desk REST API plus the Jira platform API for assignment) | REST; statuses are workflow-defined per site, with no hold or acknowledge unless the workflow adds one. Also appears under `change-management`; the incident and change files are kept separate. Problems, changes, alerts, on-call and the Incidents REST API are not covered. Several transition details are unverified |
| ManageEngine ServiceDesk Plus | `manageengine-servicedesk-plus/` | Create/find/read, edit, pick up, assign, note, add resolution, close a request of type Incident (v3 REST API) | REST; statuses and mandatory fields are instance-configured. No hold, acknowledge or documented reopen, and close is final. Group, technician and closure code are passed by name. Delete and problem or change association are not covered. Several details are unverified |

Correction recorded when PagerDuty was added: the universal concept of an open-to-resolved-to-closed state path was rewritten, because PagerDuty has no closed state and adds an acknowledged state.

Added alongside the three platforms above: the state path is now stated as sometimes workflow- or instance-defined (Jira Service Management, ServiceDesk Plus), and writes may be asynchronous (Opsgenie), so the shared concepts were reworded to say so.
